01專案總覽

這是一組個人 YouTube 播放清單自動化工具。核心是 playlist_sorter.py： 每天定時把 13 個播放清單依「頻道 A→Z、觀看數高→低」重新排序並寫回 YouTube， 全程受自製配額管理器保護；另附三個以 API Key 運作的唯讀輔助工具（歌單搜尋、重複偵測、影片搜尋）。

02系統架構圖

四層結構：入口工具 → 共用模組 → 認證機制 → Google 雲端 API。 只有主力工具 playlist_sorter.py 走 OAuth 2.0（因為需要「寫入」權限）， 其餘三個唯讀工具都使用 API Key。

圖 1 — 系統架構。quota_manager 與 log_utils 僅由主力工具鏈使用； 另外 main.py 內尚保留一段舊版 OAuth 程式（oauth_access_user()，未在主流程使用）。

03核心排序流程圖

playlist_sorter.py 的完整生命週期：啟動後立即執行一輪，之後每天 16:05 排程再跑。 每輪依「規模小 → 大」處理 13 份清單，讓配額耗盡前小清單能全數完成。 最關鍵的省配額設計：已在正確位置的歌直接跳過（0 unit），只有真的要搬移才付出 50 units。

圖 2 — 每日排序作業流程。紅框為配額保護的安全出口：一旦觸及軟上限，整輪作業立即中止， 保留 2,000 units 緩衝；隔日 16:05 從頭再跑（已排好的位置會被跳過，等於接續進度）。

04OAuth 2.0 認證流程圖

PlaylistSorter._authenticate() 的三段式策略：快取憑證 → 刷新 → 重新走瀏覽器授權。Refresh Token 失效（invalid_grant）時會自動刪除舊快取並重新授權， 不需人工介入清檔案。

圖 3 — 認證決策樹。左側是「快取＋刷新」的快速路徑（不需人工操作）； 右側是完整的瀏覽器重新授權路徑，成功後憑證回寫 token.pickle 供下次使用。

05模組詳細說明

六個模組的職責、規模與關鍵實作重點。

playlist_sorter.py核心348 行

PlaylistSorter 類別＋排程主程式。OAuth 認證（含刷新與失效自救）、分頁抓取、 本地排序（頻道 A→Z → 觀看數高→低）、逐位置搬移（跳過已正確者）、 指數退避重試（409/500/503）、軟上限熔斷。以 schedule 每日 16:05 執行。

quota_manager.py共用36 行

QuotaManager：呼叫 API 前先 consume(cost) 預扣檢查， 超過軟上限 8,000 即拋 QuotaSoftLimitExceeded。 純記憶體計數（不跨程序、不持久化）。

log_utils.py共用40 行

ColoredFormatter：依 log level 上 ANSI 色（紫/紅/黃/綠/青）， 輸出至 console。全專案共用同一個 module-level logger（DEBUG 級）。

main.py工具147 行

YouTubeAPIHandler：建構時即以 API Key 全量載入指定清單， 提供 search_keyword_in_song_list() 關鍵字搜尋（比對歌名＋頻道、 結果每段 ≤1,900 字元）。另含未使用的舊版 OAuth 方法。PyInstaller 打包目標。

check_duplicate.py工具144 行

YouTubeDuplicateFinder：抓取整份清單後以 O(n²) 標題「子字串互含」比對分組， 每組依觀看數排序並輸出「👑 保留／❌ 刪除」建議報告。僅供人工判斷，不自動刪除。

search.py工具50 行

YouTubeSearchHandler：以 requests 直接呼叫 search.list REST 端點，限定近 180 天、strict 安全搜尋， 可調結果數與排序方式。注意：每次呼叫成本高達 100 units。

06API 配額成本分析

YouTube Data API 免費配額為每日 10,000 units（太平洋時間午夜重置）。 各操作成本落差極大——「搬移一首歌」等於「讀 50 頁清單」的成本， 這正是整個配額管理設計存在的原因。

單次 API 呼叫的配額成本

單位：quota units・線性刻度（0–100）

playlistItems.list 1
videos.list 1
playlistItems.update 50
search.list 100 units

讀取類操作幾乎免費；寫入（update）與搜尋（search）是唯二的高價操作。

每日 10,000 units 的分配策略

08,000（軟上限）10,000（硬上限）
排序作業可用（≈ 最多搬移 160 首/日） 保留緩衝 2,000 units（其他用途／安全邊際）

成本一覽表

API 操作成本（units）專案內用途使用端
playlistItems.list1分頁抓取清單內容（每頁 50 筆）sorter・main・duplicate
videos.list1批次抓取觀看數／頻道（每批 50 部）sorter・main・duplicate
playlistItems.update50搬移一首歌到指定位置sorter
search.list100關鍵字搜尋近 180 天影片search

💡 情境試算：1,085 首的「YTMusic」大清單

  • 純讀取（抓清單＋詳情）：約 22 頁 × 1 ＋ 22 批 × 1 ≈ 44 units — 幾乎免費。
  • 最壞情況全部搬移：1,085 × 50 = 54,250 units — 超過 5 天的總配額。
  • 因此首次排序需靠「每日 160 首」分多天收斂；收斂後每天只需付出讀取成本＋少量新增曲目的搬移費用。
  • 清單「由小到大」處理的順序設計，確保配額斷炊前小清單能全部完成。

07問題盤點與優化建議

共 24 項發現，依「安全性 → 正確性 → 架構 → 效能 → 可維運性」五類整理， 嚴重度以標籤標示。所有項目皆為靜態研讀結果，未實際執行程式驗證。

⚡ 最優先處理 Top 5

  1. 輪替並外部化 API Key — 金鑰已明碼存於三個檔案，應視同外洩處理（項目 1）。
  2. 建立版本控制＋.gitignore — 先排除憑證檔再 git init（項目 2）。
  3. 抽出共用 YouTube client — 消除三份重複的抓取邏輯（項目 10）。
  4. 以 LIS 演算法最小化搬移次數 — 大清單首次排序可省下數千 units（項目 15）。
  5. 配額用量持久化 — 避免同日重啟後計數歸零而實際超額（項目 16）。

安全性

高風險
  1. API Key 明碼寫死，且同一把金鑰重複出現在三個檔案
    main.py:14、check_duplicate.py:127、search.py:8。 任何拿到原始碼的人都能盜用你的每日配額。
    改由環境變數（YOUTUBE_API_KEY）或 .env 讀取； 到 Google Cloud Console 輪替金鑰，並設定「API 限制」只允許 YouTube Data API。
  2. 憑證檔裸放於專案根目錄，且專案未納入版本控制、沒有 .gitignore
    client_secret.json 與 token.pickle 等同帳號操作權。 未來一旦 git init ＋ push，極易連同憑證一起外洩。
    先建立 .gitignore（排除 client_secret.json、token.pickle、 .venv/、build/、dist/、__pycache__/）再初始化 git。
  3. OAuth 憑證以 pickle 序列化儲存
    pickle 反序列化來路不明的檔案可執行任意程式碼；Google 官方範例已改用 JSON。
    改用 credentials.to_json() 儲存、 Credentials.from_authorized_user_file() 載入。

正確性與錯誤處理

中高
  1. OAuth 參數拼字錯誤，實際無效
    main.py:87 的 authorizartion_prompt_message（多了 r）， 被 run_local_server() 的 **kwargs 靜默吞掉，設定從未生效。
    更正為 authorization_prompt_message（playlist_sorter.py:76 的寫法是正確的）。
  2. 連續兩次 sort，第一次幾乎被覆蓋；且兩工具排序規則不一致
    main.py:55-56 先依觀看數排序再依（頻道, 標題）排序—— 因 sort 穩定性，前者只剩「同頻道同標題」時的 tie-break 作用，意圖不明。 且與 playlist_sorter.py:270 的排序鍵（頻道, −觀看數）不同，兩工具產出的順序不一致。
    統一為單次 sort、明確的複合 key，並抽成兩者共用的排序函式。
  3. bare except 靜默吞錯
    playlist_sorter.py:69 刪除舊 token 失敗時 except: pass， 連 KeyboardInterrupt 都會被吞掉。
    至少改為 except OSError 並記 log。
  4. API part 參數含多餘空格
    main.py:96 的 part="status, contentDetails"（逗號後有空格）， 依賴 Google 端寬鬆解析。
    改為 "status,contentDetails"。
  5. 缺少防呆：統計資料不存在時會直接 KeyError
    main.py:39 直接取 item["statistics"]["viewCount"]， 遇到隱藏觀看數／已下架影片會整支炸掉（check_duplicate.py:35 反而有做防呆）； 另外 main.py 也未處理「頁面內全是失效影片、vid_ids 為空」的情境。
    比照 check_duplicate.py 用 .get() 加預設值，空清單先跳過。
  6. HTTP 請求無 timeout、無錯誤處理；使用已棄用的 utcnow()
    search.py:17 的 requests.get() 沒有 timeout（可能永久卡死） 也沒檢查狀態碼；search.py:36 的 datetime.utcnow() 在 Python 3.12+ 已棄用。
    加 timeout=10 與 raise_for_status()； 改用 datetime.now(timezone.utc)。

架構與重複程式碼

中
  1. 「分頁抓清單＋批次抓詳情」邏輯重複實作了三份
    main.py、check_duplicate.py、playlist_sorter.py 各自維護幾乎相同的抓取迴圈，改一處要改三處。
    抽出共用 youtube_client.py（認證＋抓取＋分頁），三個工具改為呼叫端。
  2. 設定值硬編碼且散落各檔
    播放清單 ID（13 組寫死在 playlist_sorter.py:297-311、 其他檔案又各有一份）、排程時間 16:05、軟硬上限、port 8080 等均為 magic value。
    集中到 config.toml／.env，或以 CLI 參數（argparse）傳入。
  3. 建構子內執行全量網路 I/O
    main.py:10 的 YouTubeAPIHandler.__init__ 直接抓完整份清單（千首等級），物件無法在不打 API 的情況下建立，難以測試。
    改為顯式的 load() 方法或 lazy property。
  4. 死碼殘留
    playlist_sorter.py:87-113 整段註解掉的舊版 _authenticate()（27 行）； main.py:42 一行無作用的孤立字串常值；多處註解掉的舊 playlist ID 與測試碼。
    刪除（納入版本控制後歷史自然可查）。
  5. 依賴定義三處不同步
    pyproject.toml／poetry.lock（2025-11）與 requirements.txt（2024-02）版本快照不一致； search.py 直接 import 的 requests 未宣告於 pyproject.toml（僅靠間接依賴帶入）。
    以 Poetry 為唯一來源，requests 明確宣告， requirements.txt 改由 poetry export 定期重新產生。

效能與配額效率

中
  1. 搬移策略非最優：最壞需 O(n) 次 update
    目前採「逐位置對齊」，理論上限為每首歌一次 update。 1,085 首清單最壞 54,250 units（5.4 天配額）。 其實只需搬移「不在最長遞增子序列（LIS）中」的元素即可達成排序， 對「大致已排序」的清單可將搬移次數降到接近實際亂序數。
    以 LIS 計算最小搬移集合，再依序 update；每日可完成的清單數會顯著提升。
  2. 配額計數不持久化，重啟即歸零
    QuotaManager 只存在記憶體。同一天內程式重跑（手動＋排程各一次、或當機重啟） 會從 0 重新計數，實際用量可能早已超過軟上限而不自知。
    將每日用量寫入本地檔案（含太平洋時區的日期戳），啟動時載入接續計數。
  3. 重複偵測為 O(n²) 且無標題正規化
    check_duplicate.py:71-100 雙層迴圈子字串比對； 「Official MV」「【】」「feat.」等雜訊會讓真重複比不出來、假重複被誤抓。
    比對前先正規化（去括號註記、全形轉半形、去常見尾綴）， 或改用 rapidfuzz 相似度；千首等級 O(n²) 尚可接受，正規化的效益更大。

可維運性

低
  1. 沒有任何測試與 CI
    排序鍵、分段邏輯、QuotaManager 熔斷等純邏輯其實非常好測。
    先為 QuotaManager、排序 key、__generate_song_list_response() 補單元測試（不需真的打 API）。
  2. 日誌只輸出 console，長駐排程無法回溯
    腳本設計為 24 小時待命，但當機或誤動作後沒有檔案日誌可查。
    在 log_utils.py 加 RotatingFileHandler（檔案不上色、console 上色）。
  3. Formatter 直接改寫 record.msg
    log_utils.py:24 就地修改 record.msg， 未來若掛第二個 handler（如檔案）會拿到已含 ANSI 碼或重複上色的訊息。
    在 format() 內複製 record 或改以 levelname 包色。
  4. 「啟動即執行」的測試碼殘留在正式流程
    playlist_sorter.py:342-343 自註「為了測試，啟動時將立即執行一次」， 意味每次重啟腳本都會立刻消耗配額。
    改為 CLI 旗標（如 --run-now）控制。
  5. PyInstaller 打包目標已過時
    main.spec 打包的是 main.py，但主力功能已移往 playlist_sorter.py；dist/main.exe 為 2024-02 舊產物。
    更新 spec 指向主力腳本，或移除不再使用的打包產物。
  6. 多處錯字
    Credentialls、Resfreshing（main.py:70,76）、 註解「包果」應為「包裹」（playlist_sorter.py:50）。
    一併修正（其中拼字錯誤的參數名即項目 4）。
  7. 魔術數字 1900 無說明
    main.py:124 的訊息分段長度 1,900，推測是為 Discord 2,000 字元上限預留， 但沒有註解或常數名稱說明。
    提為具名常數，如 MESSAGE_CHUNK_LIMIT = 1900 # Discord 上限 2000 預留緩衝。
  8. 雙底線 name mangling 當作 private 慣例
    main.py 的 __sort_yt_playlist 等方法使用雙底線， 觸發 Python name mangling，繼承與測試時徒增困擾。
    依 PEP 8 慣例改用單底線 _method。
